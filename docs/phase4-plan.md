# Phase 4 plan: notifications, widget and Live Update (Android)

Scope: BRIEF §5 (notifications), §7 "Beyond the app" (widget, Live Update), `docs/PLAN.md` Phase 4. Android only; iOS push, widgets and the Live Activity are Phase 6 **[MAC]**, except for the iOS smoke-build proposal at the end. **Nothing here is built yet; this plan is for review.**

Starting point: the server already plans, dedupes (`notification_log UNIQUE(subscription, outage, kind, revision)`), holds for quiet hours, marks urgent, retries, checks receipts and drops dead tokens; it has a `PushProvider` interface (`LogPushProvider` in use) and a `BoundarySink` for the outage start and end signals (`LogBoundarySink`). The app registers a device with a `dev-token:<uuid>` (accepted only with `NODE_ENV=development`), asks the Android 13 permission in onboarding, shows the "notifications off" banner, and stores the notification kinds and quiet hours. The copy for all five kinds exists in `packages/shared` in sr-Latn, sr-Cyrl and en. What is missing is everything between the server and the phone, the widget and the Live Update.

## 1. Facts that shape the plan (checked 28 Oct against the current docs)

1. **Expo push on Android goes through FCM v1.** It needs: the EAS project id (for the token), the FCM service account key uploaded to EAS, and `google-services.json` in the build. The server sends to `https://exp.host/--/api/v2/push/send` (through `expo-server-sdk`), gets tickets, and fetches receipts about 15 minutes later; `DeviceNotRegistered` in a ticket or a receipt means stop sending to that token (our receipts job already does this).
2. **A message with only `data` (no title and body) is a headless background notification**: it runs the `expo-notifications` background task (defined with `expo-task-manager`, registered with `Notifications.registerTaskAsync`) in the foreground, background and terminated states. With `priority: 'high'` it may wake a device in Doze; with a short TTL it may never arrive. Expo's docs warn that Android may not deliver in Doze or when too many are sent, and say nothing about force-stop.
3. **Force-stop is final by Android's design:** a force-stopped app (and an app that MagicOS "manages automatically" and stops) does not receive FCM messages until the person opens it again. No app can work around that. The app can only (a) tell the person what to change (D.2, D.3) and (b) fall back to things that survive: a **scheduled local notification** at `starts_at` (set whenever the app learns of an outage, from a push or a sync) and a **periodic background refresh**.
4. **Android notification channels** must exist before the token is requested on Android 13+ (or the permission prompt does not appear); a push to a channel that does not exist on the device is not shown. A channel's importance cannot be changed after creation (only name and description), so the "Hitno" channel is created once, high, with the right sound.
5. **Actions** are notification categories (`setNotificationCategoryAsync`) with buttons; `opensAppToForeground: false` runs the action in the background task (that is how "Dodaj u kalendar" can work without opening the app; but see §3 step 2 for why it opens the app anyway).
6. **Live Updates are Android 16 (API 36) and newer**: `Notification.ProgressStyle`, `setRequestPromotedOngoing(true)`, `setShortCriticalText`, the `POST_PROMOTED_NOTIFICATIONS` manifest permission (non-runtime; the person can turn it off per app, `NotificationManager.canPostPromotedNotifications()` says whether we may post). Requirements: ongoing, a title, no custom views, not a group summary, not colorized, a channel above `IMPORTANCE_MIN`. OEMs may add their own criteria. **Your HONOR runs Android 15 (API 35): the promoted path cannot be verified on it**; it runs on the `Pixel_10_Pro` emulator (API 37). The phone verifies the fallback (an ongoing notification with a countdown chronometer).
7. **expo-widgets on Android** (SDK 58): the widget is TSX with `@expo/ui/jetpack-compose` components (`Box`, `Column`, `Row`, `Text`, `Image`, `LinearProgressIndicator`, buttons, a few modifiers), compiled to Compose/Glance; `createWidget(name, component, initialProps)`; the app sets its content with `updateSnapshot(props)` and `reload()`. **No timelines on Android** (iOS only), the widget code runs in an isolated runtime (no hooks, state, imports or module values), only `colorScheme` of the environment is available, and the docs do not say whether `updateSnapshot` works from a headless task. Needs a development build and `enableAndroid: true` in the plugin. So the widget cannot schedule its own state changes: something must push them (§3 step 4).
8. **The 4 KiB payload limit** applies to the whole FCM message: the data payload carries ids and the short copy, never the street list.
9. **Serbian channel names and descriptions** are visible in the system settings and must read well in the person's script; the app creates them in the chosen script (Latin by default) and renames them when the script changes (name and description can change).

## 2. Architecture

```
server: plan → notification_log (pending, deliverAt, payload{title, body, channelId, groupKey, urgent, data})
        deliver job ──▶ ExpoPushProvider (expo-server-sdk) ──▶ Expo push service ──▶ FCM v1 ──▶ phone
        receipts job ◀── tickets / receipts (DeviceNotRegistered → drop device)
        boundary job (every minute): started / ended ──▶ ExpoBoundarySink: data-only push, priority high
                                                         ──▶ (fallback) FcmDirectSink: FCM v1 HTTP, data, high priority
app:    expo-notifications: channels (5 + Hitno), categories (Detalji, Dodaj u kalendar), token → POST /v1/devices
        headless task (expo-task-manager): on data push → live-update start/stop, widget snapshot, local schedules
        local schedules: "Bez struje" at starts_at and "Struja se vratila" at ends_at, as a fallback
        periodic refresh (expo-background-task, WorkManager, ≥ 15 min): sync my outages → widget, schedules
        expo-widgets: small (primary address) and medium (up to 3 addresses), props from the snapshot store
        live-update (local Expo module, Kotlin): ProgressStyle + promoted on API 36+, chronometer ongoing below
```

- **The server stays the source of truth for what is told** (the dedupe constraint, quiet hours, urgent, revisions). The app never decides to send a kind; it only displays, groups, deep-links and falls back.
- **One `notifications` module in the app** (`src/notifications/`): channels, categories, token registration, the response listener (tap and actions), the headless task, the local-schedule fallback, and the snapshot store the widget reads. Every function is testable with the fake provider and mocked `expo-notifications`.
- **Data pushes carry only ids and times**: `{ signal: 'started' | 'ended', outageId, startsAt, endsAt, subscriptionIds }`. The headless task has the outage in the persisted query cache (the app saw it before: a `new` push preceded it) or fetches `GET /v1/outages/:id` if not.
- **The widget snapshot** is a small JSON in MMKV (`{ addresses: [{ name, status, day, window, startsAt, endsAt }], updatedAt }`) written by the sync and by the headless task; the widget is rendered from it with `updateSnapshot`. Countdown in the widget is a text set at render time ("za 2 h 10 min") and refreshed by the periodic task; no per-minute updates (Glance has none without timelines).

## 3. Build order (each step ends with lint, typecheck, tests green and a commit; a stop after step 2 for the first real push, and after step 6 for the phone session)

1. **Credentials and the real token** (needs C for the real token; builds and tests without it). Server: `ExpoPushProvider` with `expo-server-sdk` (installed at its current version with `pnpm add`, not pinned here), chunking, tickets, receipts, `DeviceNotRegistered`; chosen by `PUSH_PROVIDER=expo|log` (default `log` outside production), the Expo access token optional (`EXPO_ACCESS_TOKEN`, documented in `.env.example`). The server refuses `dev-token:` tokens outside development as today and refuses `ExponentPushToken` in development unless `ALLOW_REAL_PUSH_IN_DEV=true` (so a local stack never pushes to a real phone by accident). App: `expo-notifications` and `expo-task-manager` via `npx expo install`; `google-services.json` and the plugin in `app.json` (icon: a white 96×96 bolt, colour the lime accent); `getExpoPushTokenAsync({ projectId })` after the permission, registered through the existing `/v1/devices` flow (the push-token takeover already exists); the dev build keeps `dev-token:` when there is no project id, so the emulator against the mock still works. Prebuild and a new debug build (one native build, arm64 for the phone and x86_64 for the emulator, as in Phase 3). Tests: the provider against a recorded Expo response fixture; token registration and re-registration; the dev/real token guard on the server.
2. **The four kinds, Hitno, actions, grouping, deep links, quiet hours in the UI.** Channels created at app start, in the person's script: `nova` ("Nova isključenja", "Novo najavljeno isključenje za vašu adresu"), `podsetnik` ("Podsetnik uveče", "Sutra bez struje: podsetnik dan ranije"), `izmena` ("Izmene", "Promena vremena ili vraćanje otkazanog isključenja"), `otkazano` ("Otkazano", "Isključenje je otkazano"), `hitno` ("Hitno", "Isključenje počinje za manje od 2 sata", high importance, bypasses nothing: Do Not Disturb is respected); the server's `CHANNEL[kind]` ids are aligned to these. Categories: `outage` with **Detalji** (`opensAppToForeground: true`, deep link `strujaalert://outage/{id}`) and **Dodaj u kalendar** (opens the app and then the system add-event screen: the calendar intent needs an activity, so the action cannot be fully background; the app comes up on the detail with the calendar sheet over it). Grouping: Android group key per address (the server's `groupKey`), with an app-made summary notification "3 obaveštenja za Trebinjska 34" when more than one is showing (Android needs the summary to collapse the group). Deep links: `strujaalert://outage/{id}` opens the detail sheet from a cold start too (the router already handles the scheme; the test is that a notification tap from a killed app lands on the sheet, not on Početna). Quiet hours and kinds are already on the server; the Podešavanja screen shows "Hitna obaveštenja stižu i noću" under quiet hours, and the "notifications off" banner's **Uključi** opens the system notification settings of the app. Tests: channel names in all three scripts, the category registration, the response listener (tap, Detalji, Dodaj u kalendar), the deep-link parser, the group summary. **Stop here: first real push to the phone** (step 1's credentials in place): one notification of each kind from the local server with `ALLOW_REAL_PUSH_IN_DEV=true`, phone on USB.
3. **Outage started and ended: the data push, the headless task, and the fallbacks.** Server: `ExpoBoundarySink` (data-only message, `priority: 'high'`, `ttl` 1 hour for a start and 15 minutes for an end, one message per device), keeping `started/ended` idempotent (the row claim exists). App: the headless task (defined at module scope in the entry file, registered after the token) that on `started` shows the Live Update (step 5) and refreshes the widget (step 4), on `ended` dismisses it and refreshes; the same code runs from the foreground listener. **Fallback 1 (in the app, always on):** when the app learns of an outage for a saved address (a `new`/`changed` push, a sync, or adding the address), it schedules a local notification at `starts_at` ("Bez struje: Trebinjska 34, povratak u 16:00", channel `hitno`, ongoing look, the same actions) and one at `ends_at` ("Struja se vratila"), and cancels them on `cancelled`, on a change, and when the real data push arrives first. Local schedules survive the app being killed and Doze (they are alarms), but not a force-stop. **Fallback 2 (on the server, behind a flag):** `FcmDirectSink` sends the same data message straight to FCM v1 with the service account key (`FCM_SERVICE_ACCOUNT_JSON` in the environment, never in git) and `android.priority = high`, for the case that Expo's path turns out slower or lossy for data-only messages; chosen by `BOUNDARY_SINK=expo|fcm|log`. Tests: the sink payloads, the headless task's decisions with a fake notification module, the schedule and cancel logic (the one thing that must never happen: a "Bez struje" alarm firing for a cancelled outage).
4. **The widget** (`expo-widgets`, `enableAndroid: true`): `StrujaSmall` (2×2: the primary address: status word and colour, day, window, "za 2 h 10 min" or "povratak u 16:00") and `StrujaMedium` (4×2: up to three addresses, one row each), both reading the snapshot props, with the design tokens (flat status fills, Onest is not available in Glance: the system font), `initialLayout` for the first render before the app opened, a tap opens the app (the detail when there is one outage). Updates: on every app sync (`useHomeData`), from the headless task (`started`, `ended`, and after any push), from the periodic `expo-background-task` (every 15 minutes while an outage is within the next 24 hours, else hourly), and on the day change. "Imminent" (−24 h) comes from the periodic task, not from a push (the server has no −24 h signal; adding one is possible later). Tests: the snapshot builder for every status, the props for one and three addresses, the refresh triggers; the rendering is checked on the emulator by screenshots in light and dark (Maestro cannot see widgets; adb screenshots of the home screen).
5. **The Live Update** (local Expo module `apps/mobile/modules/live-update`, Kotlin, with a config plugin that adds `POST_PROMOTED_NOTIFICATIONS`): `start({ id, title, text, startsAt, endsAt, deepLink })` and `stop(id)`. On API 36+: `Notification.ProgressStyle` with the progress from `startsAt` to `endsAt`, `setRequestPromotedOngoing(true)`, `setShortCriticalText("1 h 12 min")`-style text refreshed only when the task runs (the chip shows a countdown by itself from `setWhen` + chronometer), `setOngoing(true)`, channel `u_toku` ("U toku", default importance, silent). Below API 36: the same content as an ongoing notification with `setUsesChronometer(true)` + `setChronometerCountDown(true)` to `endsAt` (the countdown ticks without updates), dismissed at `ends_at` by the data push or the local schedule. If `canPostPromotedNotifications()` is false on API 36+, it posts the fallback and the app's Podešavanja offers "Uključi Live Update" (`Settings.ACTION_MANAGE_APP_PROMOTED_NOTIFICATIONS`). JS API typed, with a test of the arguments; the Kotlin is exercised on the emulator (promoted) and the phone (fallback). Also starts locally when the app is in the foreground at `starts_at` (no push needed).
6. **Phone verification session** (§5) and the **MagicOS card** in the app (§5). Stop for review.
7. **iOS smoke-build proposal** (short, **[MAC]**): what a Mac session needs (Xcode 26.4+, the Apple Developer account, `eas credentials` for APNs, `expo-notifications` iOS permission flow, `timeSensitive`, the Live Activity push-to-start and the token table). A proposal document, no code.

## 6. Risks

- **Expo's data-only path on Android is thinly documented** (Expo's own page does not describe it; the SDK page does): if headless delivery is late or lost, the direct FCM sink (step 3) replaces it for the signals, at the cost of holding the service account key on our server (it is there anyway for EAS; it stays in the environment file, never in git).
- **MagicOS:** the first-run default may stop the app from being woken at all. Then the real fix is the person's settings, and the plan's answer is the MagicOS card plus the local alarms (which MagicOS also respects less than stock Android: to be measured). This is the biggest unknown and the first thing measured on the phone.
- **Force-stop cannot be worked around.** Documented as a limit.
- **Live Updates on the phone:** not possible on Android 15. If HONOR ships Android 16 for the Magic6 Lite during the phase, the promoted path gets re-tested; otherwise its only evidence is the emulator.
- **expo-widgets from a headless task:** undocumented; verified in step 4 first. If `updateSnapshot` needs the app's main runtime, the widget is refreshed by the periodic task and by the app, and the push only triggers that task (a delay of up to a minute).
- **Widget rendering limits** (no custom font, few modifiers, "View not found" for anything else): the widget will look plainer than the app; the design tokens' colours and the bolt image carry the identity.
- **Payload size** (4 KiB): the data push carries ids only.
- **Channel importance is fixed at creation:** the channel ids are final from step 2 on; a change later means a new id (the old channel is deleted).
- **Expo push rate limits** are far above our volume; the Expo access token (optional) protects against someone else pushing with our project id.
- **The service account key** is the one real secret added by this phase: in the password manager and in the server's environment file only.
